# Maverick Wall

A self-hosted family calendar wall display. One household runs one container on
their own hardware. Screens point at it and run unattended for months.

**The calendar is the product.** Everything else is extra. There is no cloud
version — do not build for one.

---

## Hard rules

Violating any of these is a failed task.

1. `packages/calendar` and `packages/core` import no vendor SDK, framework, or
   runtime API beyond the standard library. Need I/O? Define a port.
   `packages/core/src/globals.d.ts` is the complete, auditable list of runtime
   surface core depends on.
2. Display targets ES2019. No `:has()`, container queries, subgrid, `@layer`,
   top-level await, `structuredClone`.
3. No third-party origins in the display bundle or HTML. No CDN, no web fonts,
   no analytics. Everything ships in the image — it must work with no internet
   beyond the calendar feeds themselves.
4. Every user-supplied URL goes through the SSRF-guarded Fetcher.
5. Zod at every boundary. Reject, do not coerce.
6. No secrets in the repo, the image, or logs.
7. Migrations forward-only, generated by Drizzle, run on boot behind a file
   lock. A shipped migration is never edited — somebody's kitchen calendar has
   already run it.
8. One container. If you think you need Redis, you don't.
9. **Never brick the kitchen calendar.** Every failure degrades to reduced
   function with a clear on-screen message. Never a refusal to start, never a
   blank screen.
10. Assume somebody will expose this to the internet, badly. Secure defaults, no
    default credentials, in-app rate limiting.
11. Assume you can never reach the user's machine. Backups trivial, errors
    self-diagnosable.
12. Home Assistant integration is READ-ONLY. No service calls, no control.

## Stack — decided, do not relitigate

TypeScript strict · Node LTS · pnpm monorepo · Hono · SQLite via better-sqlite3
(WAL) · Drizzle · Better Auth · in-process scheduler · local filesystem blobs ·
ical.js for parsing · Zod · vanilla TS display (ES2019, no framework) · Vitest.

The admin UI is also **no framework** — vanilla TS plus a small hash router.

## Layout

```
packages/calendar/   Pure ICS parsing + recurrence expansion. MIT, own repo later.
packages/core/       Pure domain: SSRF guards, civil dates, shift, scheduler, ports.
apps/server/         Hono + SQLite + scheduler + jobs. The single process.
apps/display/        Not started. Vanilla TS wall renderer.
apps/admin/          Not started. Vanilla TS settings UI.
```

`packages/core/src/domain/shift/` is deliberately self-contained: nothing else
in core imports it, and it imports nothing from core beyond civil dates. That
seam exists so it can be extracted later without a refactor, and so a household
with no shift worker can have the whole feature switched off.

## How to work on this

### Verification is the job

This project has found **eight real bugs**, and the pattern in how is the most
useful thing in this document:

| Bug | Found by |
|---|---|
| One malformed event killed a whole feed | A hostile synthetic fixture |
| U+200B in event titles | A real school district feed |
| `TZID:US Eastern` unresolvable | The same real feed |
| Duplicate warnings, 2× per event | **Reading a committed snapshot with nothing failing** |
| **Link-local reachable via the LAN opt-in** | An integration test against a live server |
| gzip responses never decompressed | Pointing it at real Google Calendar |
| Setup gate deadlocked sign-up | A route test with a stubbed session |
| `/admin/*` didn't protect `/admin` | The same test |

None of those were found by typechecking. Several were found *while tests were
green*. The link-local one is the sharpest: a unit test asserted
`isLocalNetwork('169.254.1.1') === true` — it was confidently testing the bug,
in a file with 88 passing assertions, and only a real redirect exposed it.

So: **prefer tests that touch something real.** A local HTTP server over a stub.
A temp SQLite file over a mock. Actual fixture bytes over invented ones.

### Commands

```bash
pnpm test          # builds first, then tests. This is what CI runs.
pnpm test:quick    # skips the build; fine while iterating in one package
pnpm -r build
```

`pnpm test` builds because **vitest only transpiles** — it never resolves a
dependency's declarations. `packages/calendar` passed 153 tests for days over
`ical.js` imports that `tsc` rejects outright. Do not remove the build step.

### Running it

```bash
export DATA_DIR="$PWD/data"          # absolute; see the trap below
pnpm --filter @maverick-wall/server build
node apps/server/dist/main.js
```

CLI tools, all in `apps/server/dist/tools/`:

```
add-source "Family" "<ics-url>" [--allow-lan] [--allow-loopback] [--allow-http]
add-screen "Kitchen" | --list | --revoke <id>
diagnose-source [source-id]      why a feed is failing, with the parser's own message
analyse-titles [source-id]       which titles look like a work schedule
enable-shift --from-calendar <source-id> [--person Name]
             --pattern <YYYY-MM-DD> [--person Name]
             --off
```

**`DATA_DIR` must be absolute.** `pnpm --filter` runs scripts from the package
directory, so a relative path means a different database depending on who's
asking. That silently split one installation into two, and surfaced three
commands later as "that pairing link is not valid". Every entry point now prints
the database it opened — if two disagree, that's why.

## Conventions

**Never throw across a boundary.** `expandCalendar` returns
`Result<NormalizedEvent[], CalendarError>`. The fetcher returns a typed outcome.
Decryption returns a result. A wall display cannot handle an exception, and the
household cannot read a stack trace.

**Errors are written for someone standing in a kitchen.** Not for a log reader.
`testFeed` returns a *suggestion* for every failure mode, because "PARSE_FAILED"
is not a diagnosis. When a message can name the fix, it should.

**Warnings and logs never contain event content or credentials.** There are
tests asserting this. Only hostnames, never paths — the path is the credential.

**Comments explain why, not what.** Especially where a choice looks arbitrary:
why equal jitter rather than full, why block count rather than coverage, why the
loopback flag is separate from the LAN flag.

**Recurrence is computed on wall-clock, then anchored.** RFC 5545 defines
recurrence over local clock readings. A weekly 09:00 event is a promise about
what the kitchen clock says. Zones come from `Intl`, not from the feed's
VTIMEZONE, which is often stale or absent.

**`DTEND` is exclusive.** A one-day all-day event on the 15th has `DTEND` of the
16th. Rendering `startUtc..endUtc` inclusive puts every birthday on the wrong
day. This is the single most common ICS bug.

## Current state

**463+ tests passing.** calendar 153 · core 213+ · server 144+.

Working end to end: a real Google feed fetched through the SSRF guard,
gzip-decoded, recurrence expanded server-side, stored with the URL encrypted at
rest, served as a manifest over HTTP with an ETag. 166 events, zero warnings.

**Done:** ICS engine · SSRF guard (URL + DNS-pinned fetcher) · shift rotation
(per person, pattern or calendar-derived, with title analysis) · secrets at rest
· 21-table schema · migrations behind a file lock · scheduler · ICS sync ·
`/healthz` · `/d/manifest` · display tokens · session gating.

**Not started:** `apps/display` · `apps/admin` · weather (NWS) · interrupts and
alerts · ws push · Docker image · HA add-on.

**Unverified:** `apps/server/src/auth/better-auth.ts`. Written against a shim.
Every other module has been executed.

## Open decisions

- **First-run wizard completion criteria.** Blocked until "configuration is
  complete" — is that account + timezone, or does it require a calendar too?
- **HA calendar entities as a source type.** Distinct from ingress. If the
  household already has calendars in Home Assistant, re-syncing the same ICS is
  wasteful. Needs a new source kind with its own fetch path.
- **Display density.** A work feed marks *every* day. Matched shift events are
  consumed out of the agenda, but a NEXT row still needs an opinion about how
  many events per day it can show before it stops being readable.

## The design file

`maverick-wall-design-directions.html` (in the project, not the repo) defines
four themes as CSS custom property sets: **Board** (dark, amber), **Kitchen
Slate** (warm dark, gold), **Paper Almanac** (light paper, red), **Glance**
(near-black, white).

Decided: **Board as default, Almanac scheduled for daylight hours.** Board's
shift hues separate best at ten feet; Almanac at 2am is a lamp. Themes are pure
token sets with no logic differences.
